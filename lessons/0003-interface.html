Lição 0003 · Trilha I — Estrutura

Interface é mais que a assinatura

Na lição 0002, o caller 3 quebrou porque conferiu o saldo depois de commitar. Nenhuma assinatura Java dizia que a ordem importava — e a regra existia mesmo assim. Esta lição é sobre onde essas regras moram, e o que fazer com elas.

Tempo: ~20 min · Código: code/0003-interface/InterfaceDemo.java (roda com java InterfaceDemo.java) · Glossário: interface, module, depth, seam

Primeiro, de memória · lição 0002

Você abre um arquivo novo e encontra um module chamado AuditLog: um método público, 400 linhas de implementação. O que essas duas contagens te dizem sobre a depth dele?

As duas contagens são da implementação, e SKILL.md:62 corta isso pela raiz: "Depth is a property of the interface, not the implementation." Foi exatamente por isso que a lição 0002 mediu o PaddedLedger — mesma interface, mesmo comportamento, 2,5× mais "profundo" pela métrica rejeitada, e zero comportamento a mais.

Mas agora repare no que a resposta certa te obriga a admitir: se depth é o custo para o caller, você precisa saber o que o caller realmente tem que aprender. Um método público não quer dizer uma unidade de interface. É isso que vamos medir hoje.

1 · A intuição

Duas chaves de luz na mesma parede. Mesmo formato, mesmo plástico, mesmo clique. Você não consegue distinguir uma da outra olhando.

A da esquerda

Você aperta. A luz acende.

Aperta de novo, apaga. Não tem mais nada para saber.

A da direita

Você aperta. A luz acende.

Mas se apertar antes de trinta segundos desde a última vez, o disjuntor cai e a geladeira desliga. Isso não está escrito em lugar nenhum. O eletricista sabia.

As duas chaves têm o mesmo formato. Elas não têm a mesma interface. E a diferença entre as duas palavras é a lição inteira: formato é o que você vê; interface é tudo que você precisa saber para usar sem estragar nada.

A prova de que a regra dos trinta segundos é parte da chave, e não um detalhe externo a ela: se ninguém te contar, você derrete o jantar. Uma regra que decide se você acerta ou erra não é documentação — é parte do produto.

Para uma criança de cinco anos

Um brinquedo tem um botão. Apertar o botão faz barulho. Isso é o botão.

Mas se você apertar o botão com o brinquedo de cabeça para baixo ele quebra — e ninguém te avisou. A regra "não de cabeça para baixo" faz parte do brinquedo do mesmo jeito que o botão faz, mesmo que ela não tenha forma, nem cor, nem lugar para apertar.

2 · O mecanismo

A definição do repositório de skills é a mais radical do glossário inteiro:

Interface — everything a caller must know to use the module correctly: the type signature, but also invariants, ordering constraints, error modes, required configuration, and performance characteristics.

codebase-design/SKILL.md:16 verbatim

Leia devagar as três primeiras palavras: everything a caller must know. Não é everything you wrote down. Não é everything the compiler enforces. A interface é definida pelo que o caller precisa, não pelo que alguém teve o cuidado de declarar.

Isso tem uma consequência desconfortável e imediata: a interface de um module não muda quando você escreve a documentação. Ela já estava lá. Documentar não adiciona interface; só torna visível a que já estava sendo cobrada de quem chama.

E o _Avoid_ do glossário diz a mesma coisa por outro lado: evite API e signature — "too narrow — they refer only to the type-level surface". Quando alguém no seu time diz "a API não mudou", quase sempre quer dizer "a assinatura não mudou". São afirmações diferentes, e a segunda não implica a primeira.

O repositório reforça isso recusando explicitamente a leitura estreita:

"Interface" as the TypeScript interface keyword or a class's public methods: too narrow — interface here includes every fact a caller must know.

codebase-design/SKILL.md:108, seção "Rejected framings" verbatim

São seis categorias na lista. A assinatura é uma delas.

A ligação com a lição 0002, que fecha as duas

Depth é comportamento por unidade de interface aprendida. Se interface inclui ordem, modos de erro e invariantes, então essas coisas entram no denominador.

Ou seja: um module com um método só pode ser shallow, se esse método vier acompanhado de quatro regras que você tem que carregar na cabeça. Contar métodos públicos nunca foi medir interface — era só a parte fácil de contar.

3 · Em Java

Duas classes. A mesma interface Java, os mesmos três métodos, as mesmas assinaturas. Um caller escrito contra o tipo não consegue distinguir uma da outra:

public interface Ledger {
    void post(Transfer t);
    void reconcile();
    BigDecimal total();
}

A diferença está em quando a taxa chega à conta de tarifas do banco.

StrictLedger acumula
public void post(Transfer t) {
    book.add(debito(t));
    book.add(credito(t));
    accrued = accrued.add(t.fee());
}

public void reconcile() {
    book.add(new Entry(FEES, accrued, ...));
    accrued = BigDecimal.ZERO;
}
EagerLedger lança na hora
public void post(Transfer t) {
    book.add(debito(t));
    book.add(credito(t));
    book.add(new Entry(FEES, t.fee(), at));
}

public void reconcile() {
    /* nada a varrer */
}

Agora um caller, escrito uma vez contra Ledger, rodado contra os dois:

static BigDecimal naiveCaller(Ledger ledger, List<Transfer> batch) {
    batch.forEach(ledger::post);
    return ledger.total();
}

Saída capturada de java InterfaceDemo.java:

A. Same interface, same signatures, different interface
   methods declared on Ledger ........ 3
   signatures that differ ............ none

   naive caller  post, post, total()
   against EagerLedger ...............      0.00   OK
   against StrictLedger ..............     -5.00   MONEY DESTROYED

   informed caller  post, post, reconcile, total()
   against EagerLedger ...............      0.00   OK
   against StrictLedger ..............      0.00   OK

   rule that decides which is safe ... not in the type

Cinco reais evaporaram — duas taxas de R$ 2,50 debitadas do pagador e nunca creditadas em lugar nenhum. A invariante de partidas dobradas, que na lição 0002 era o critério de "não criar nem destruir dinheiro", foi violada em silêncio. Nenhuma exceção, nenhum log, nenhum teste vermelho: só um total que fecha errado.

E repare no que não aconteceu: o compilador não reclamou de nada. Ele não tinha do que reclamar. As assinaturas são idênticas. A regra que decide entre R$ 0,00 e dinheiro destruído — "chame reconcile() antes de total()" — é uma ordering constraint, e ela não tem onde morar em Java. Mora num comentário, num Confluence, ou na cabeça de quem escreveu.

Por que este é o bug mais caro que existe

Um NullPointerException aparece. Um teste vermelho aparece. Uma ordering constraint violada não aparece — ela produz um número plausível.

É por isso que a lição 0002 escolheu o domínio bancário: R$ -5,00 num ledger de partidas dobradas é impossível por construção, e ainda assim aqui está ele, produzido por código que compila.

A correção muda exatamente uma coisa

Não vamos renomear nada, não vamos extrair helper, não vamos adicionar validação. Uma única mudança: a ordem sai da prosa e entra no tipo.

A ordem virou um tipo mesmo comportamento do StrictLedger
public final class OpenBooks {
    public OpenBooks post(Transfer t)  { ...; return this; }
    public SettledBooks reconcile()   { ...; return new SettledBooks(book); }
}

public final class SettledBooks {
    public BigDecimal total() { ... }
}

total() não existe em OpenBooks. post() não existe em SettledBooks. E o único jeito de obter um SettledBooks no programa inteiro é chamar reconcile(). A regra não foi documentada melhor — ela deixou de ser documentação.

B. The one change — ordering moved into the type
   post, post, reconcile, total() ....      0.00   OK
   total() declared on OpenBooks ..... false
   post() declared on SettledBooks ... false
   only producer of SettledBooks ..... OpenBooks.reconcile()

"Não compila" é uma afirmação verificável — então vamos verificar

Dizer que algo não compila é fácil. O programa desta lição compila o próprio arquivo para um diretório temporário, escreve um caller que pede total() cedo demais, chama o javac de verdade em cima dele e imprime o diagnóstico real:

C. Does the wrong order compile? Ask javac.
   caller asks total() too early ..... REJECTED

   WrongOrder.java:6: error: cannot find symbol
           return books.total();
                       ^
     symbol:   method total()
     location: variable books of type OpenBooks
   1 error

Isso é o javac falando, não uma saída escrita à mão para parecer saída. O programa usa ToolProvider.findFirst("javac") em tempo de execução — o mesmo compilador que rodou o arquivo. Se você rodar de outro diretório ele avisa que pulou, em vez de fingir.

Contando o que sobrou — e é aqui que a lição fica honesta

Tentação natural: concluir que "então basta colocar tudo no tipo". Não basta — e antes de mostrar o placar, vale dizer como cada linha dele foi obtida, porque nem todas são medição.

Três são derived: ordem, modos de erro e configuração exigida saem de perguntas ao JVM — respectivamente, se total() some do tipo anterior; quantas exceções verificadas post declara; quantos parâmetros o construtor público exige. Três são given: assinatura de tipo sempre existe, e invariantes e performance não têm construção nenhuma em Java para se refletir sobre. O programa marca cada linha com qual das duas ela é, e o placar é a soma das seis — não um número digitado.

D. Which of the six categories does the type check?
   1 type signature .................. given    yes
   3 error modes ..................... derived  no
   4 required configuration .......... derived  yes
   5 invariants ...................... given    no
   6 performance characteristics ..... given    no

   2 ordering, StrictLedger .......... derived  no
   2 ordering, Open/SettledBooks ..... derived  yes

   checked exceptions on post ........ 0
   public constructor parameters ..... 1

   score before section B ............ 2 of 6
   score after section B ............. 3 of 6

Três de seis. Depois de uma refatoração que a lição está vendendo como uma vitória. E repare que a linha da ordem aparece duas vezes, uma para cada desenho: no para o StrictLedger, yes para o par OpenBooks/SettledBooks. É essa única diferença que separa 2 de 3. As outras três continuam onde estavam — e a categoria 4 já estava no tipo desde a lição 0002, porque o Clock chega pelo construtor. Não foi mérito desta lição; foi mérito do seam da lição 0001.

O que fazer com as três que sobraram

Não existe truque de tipo para "o ledger sempre soma zero" em Java. O que existe é escolher onde a regra é checada, e a ordem de preferência é sempre a mesma:

compilador (grátis, imediato, impossível de ignorar) → teste (barato, roda no CI) → runtime (caro, mas ainda dentro de casa) → incidente (o cliente descobre por você).

A seção B moveu uma regra do quarto degrau para o primeiro. As outras três descem só até o segundo ou terceiro, e admitir isso é parte de saber a diferença.

4 · A fonte primária

Antes de puxar o crédito, o contra-dado — e ele é constrangedor para o enquadramento que acabamos de usar.

Parnas não diz o que o repositório diz

A frase mais citada do paper de 1972 é esta:

Every module in the second decomposition is characterized by its knowledge of a design decision which it hides from all others. Its interface or definition was chosen to reveal as little as possible about its inner workings.

Parnas, relatório técnico CMU, 1971, p. 17 verbatim, PDF conferido

Was chosen. Para Parnas, a interface é um artefato autoral — algo que você decide revelar. Para o repositório, a interface é tudo que o caller precisa saber, quer alguém tenha decidido revelar, quer não.

Essas duas frases descrevem objetos diferentes. Pela leitura de Parnas, o StrictLedger tem uma interface pequena — três métodos — que por acaso foi mal escolhida. Pela do repositório, ele tem uma interface grande, porque a regra de ordem entra na conta mesmo sem estar escrita. Não são a mesma afirmação, e fingir que são seria exatamente o erro que a lição 0002 documentou.

Dito isso — a ponte entre as duas existe, e está no mesmo paper, três parágrafos depois. Parnas pega o próprio módulo que ele acabou de projetar e o critica:

Hindsight now suggests that this definition reveals more information than necessary. While we have carefully hidden the method of storing or calculating the list of circular shifts, we have indicated an order to that list. […] By prescribing the order for the shifts we have given more information than necessary and so unnecessarily restricted the class of systems that we can build without changing the definitions.

Parnas, relatório técnico CMU, 1971, pp. 17–18 verbatim, PDF conferido

Repare no que ele está tratando como informação revelada: uma garantia de ordenação. Não um método, não um tipo, não uma assinatura. Uma ordem. Em 1971, num paper que não conhecia a palavra interface no sentido que usamos hoje, Parnas já contava ordem como parte do que a definição de um módulo entrega ao mundo.

Então a posição honesta é esta: a definição de seis itens do repositório não está no Parnas. Mas a categoria mais surpreendente dela — ordering constraints — está, e está pela mão do próprio autor se autocriticando. Isso é bem mais forte do que uma citação de apoio: é o coiner do campo aplicando o critério a si mesmo e se dando errado.

Três precisões que quase todo mundo erra ao citar este paper

1. O termo "information hiding" não é cunhado aqui. Parnas escreve, na seção "The Criteria": The second decomposition was made using "information hiding" [4] as a criteria. As aspas e a referência são dele. A referência [4] é Parnas, D. L., "Information Distribution Aspects of Design Methodology", Technical Report, Department of Computer Science, Carnegie-Mellon University, Pittsburgh, Pa., 1971. Also to be presented at the IFIP Congress 1971, Ljubeljana, Yugoslavia. lista de referências, p. 25, conferida Ou seja: o critério é enunciado no paper famoso; o termo vem de um relatório companheiro anterior, também dele.

2. O que ele propõe não é "quebre em partes pequenas". A conclusão, verbatim: "We propose instead that one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others." p. 24 A unidade de modularidade é uma decisão de projeto, não um tamanho.

3. As citações acima são do relatório de 1971, não da CACM de 1972. O paper publicado é Communications of the ACM, Vol. 15, No. 12, dezembro de 1972, pp. 1053–1058. O texto que foi lido e citado aqui é o relatório técnico da Carnegie-Mellon de 1971, do qual a publicação de 1972 é a versão editada; os números de página acima são páginas do relatório. Acredita-se que o texto seja idêntico, mas isso não foi diferenciado linha a linha. Se você for citar página, cite a da CACM e confira lá.

E a crítica, que também é nossa e não de um crítico nomeado: "esconda as decisões que provavelmente vão mudar" exige acertar a previsão. Quando você erra, a abstração cobra e não paga — é o mesmo objeto que o smell Speculative Generality do Fowler descreve, e volta na lição 0005. nossa síntese

5 · O paralelo com IA

Para um agente, a distância entre assinatura e interface não é um detalhe de estilo. É a superfície inteira onde ele adivinha.

Um humano que herda o StrictLedger tem saídas: lê o código-fonte, pergunta no Slack, lembra do incidente de março. Um agente tem a descrição da tool e mais nada. Se a ordering constraint não está literalmente escrita ali em tokens, ela não existe para ele — e ele vai produzir o caller ingênuo, que compila, roda, e destrói cinco reais.

A Anthropic chega ao mesmo lugar por outro caminho, com o vocabulário dela:

Similar to the functions of a well-designed codebase, tools should be self-contained, robust to error, and extremely clear with respect to their intended use.

Anthropic Engineering, "Effective context engineering for AI agents", 29 set. 2025 verbatim

No mesmo texto, o modo de falha que eles nomeiam é "bloated tool sets that cover too much functionality or lead to ambiguous decision points". verbatim, mesma fonte Um ambiguous decision point é exatamente o que a nossa interface Ledger de três métodos apresenta: dois caminhos igualmente plausíveis, e nenhum sinal no tipo dizendo qual.

O Building effective agents chama isso de ACI — agent-computer interface — e argumenta que ela merece o mesmo investimento de projeto que uma interface humano-computador, incluindo o conselho de "put yourself in the model's shoes" e o de desenhar os argumentos de forma que o erro seja difícil de cometer. "put yourself in the model's shoes" verbatim; o resto é paráfrase

Onde este paralelo é nosso, e onde não é

Verificado: as citações acima, verbatim, nas fontes dadas.

Nossa analogia: o mapeamento "o que não está na assinatura" ↔ "onde o agente alucina". Uma verificação de termos no texto completo de "Writing effective tools for agents" por deep, shallow, module, information hiding, Ousterhout e Parnas retornou nenhum presente. A Anthropic não desce à literatura de Parnas; o enquadramento é nosso.

E o contra-sinal: a posição declarada deles é que tools de agente exigem repensar a prática de API, não herdá-la — "instead of writing tools and MCP servers the way we'd write functions and APIs for other developers or systems, we need to design them for agents". O argumento é que uma tool é um contrato entre um sistema determinístico e um consumidor não determinístico, e portanto não é uma API com outro caller.

Mas há um ponto onde a analogia fica mais forte do lado do agente, não mais fraca. Para o humano, cada fato não escrito da interface custa uma vez: ele aprende e guarda. Para o agente, a descrição da tool é reenviada em tokens a cada turno — e a lição 0002 já mostrou a Anthropic medindo isso em 150.000 tokens contra 2.000. O custo da interface deixa de ser cognitivo e vira fatura. Um fato que você não escreveu é adivinhado; um fato que você escreveu é pago, sempre.

O que sugere um corolário incômodo, e nosso: a mesma pressão que faz você querer descrições curtas é a que faz o agente adivinhar. A saída é a mesma da seção 3 — não documentar melhor, e sim tornar o estado ilegal inexprimível, para não ter o que documentar. nossa inferência

6 · Retrieval

De memória. Errar aqui é o que faz a lição durar.

Pergunta 1 de 3

Você escreve, no Javadoc de post, que reconcile() deve ser chamado antes de total(). O que aconteceu com a interface do module?

Interface é everything a caller must know. O caller sempre precisou saber. Documentar não cria interface — torna visível a que já estava sendo cobrada.

A última opção erra por outro motivo e vale reparar: o Javadoc é um lugar legítimo para a regra morar. O erro é achar que escrever mudou o tamanho do que o caller carrega. Não mudou. Só mudou a chance de ele descobrir sem quebrar nada.

Pergunta 2 de 3

Depois de OpenBooks / SettledBooks, quantas das seis categorias o compilador verifica — e por quê?

Somado pelo programa a partir de três perguntas ao JVM, não estimado: score after section B ... 3 of 6. A configuração já estava no tipo desde a lição 0001, porque o Clock chega pelo construtor — mérito do seam, não desta refatoração.

Modos de erro, invariantes e performance seguem em prosa. Uma lição que dissesse "seis" estaria vendendo o próprio truque melhor do que ele é.

Pergunta 3 de 3

Qual é a diferença entre o que Parnas escreveu e o que o repositório define?

"Its interface or definition was chosen to reveal as little as possible" — interface como artefato autoral. O repositório diz everything a caller must know, escrito ou não. Objetos diferentes.

A segunda opção é a armadilha, e é o inverso do que aconteceu: Parnas inclui ordem, e de forma memorável — ele critica o próprio circular shifter por ter revelado uma ordenação desnecessária.

Recall livre — por que "documentar melhor" não reduz o preço da interface, e o que reduz?

Porque o preço é pago por quem chama, e o que ele paga é a quantidade de fatos que precisa carregar para acertar. Escrever esses fatos num Javadoc muda onde eles estão guardados, não quantos são. O caller ainda precisa ler, entender, lembrar e aplicar — e a chance de falhar em qualquer um desses quatro passos continua maior que zero.

O que reduz de verdade é tornar o fato desnecessário. Duas formas, em ordem de preferência:

1. Absorver — o module passa a fazer sozinho o que exigia a regra. Foi o EagerLedger: sem acumulação, a ordem some porque não há o que ordenar. 2. Tornar inexprimível — o estado errado deixa de existir como valor legal. Foi o OpenBooks/SettledBooks: a regra não é obedecida, ela é impossível de desobedecer.

E o teste que você aplica amanhã, no seu código: se eu apagasse todo o comentário desta classe, o que um colega competente erraria? Cada item dessa lista é uma unidade de interface que você está cobrando sem cobrar visivelmente — e é candidata a virar tipo.

Para onde isso vai

  • 0004 — Adapter, e seams internos vs externos. O Clock chega pelo construtor, e por isso é interface — required configuration, categoria 4. Mas nem toda dependência deveria subir até lá. A regra que decide é "um adapter é um seam hipotético; dois são um seam real".
  • 0005 — O deletion test. A técnica de varredura: dado um codebase inteiro, onde a interface está cobrando mais do que entrega.

Eu sou seu professor aqui. Se alguma parte não fechou, isso é defeito da lição e não seu — me diga qual trecho e eu reescrevo. Perguntas boas para agora: "o padrão OpenBooks/SettledBooks tem nome?", "como faço isso em Spring, onde tudo é bean singleton?", "quando o tipo extra custa mais do que a regra em prosa?", ou "aplica as seis categorias numa classe do meu código".
