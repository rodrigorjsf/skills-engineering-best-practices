Lição 0001 · Trilha I — Estrutura

Seam

O lugar onde você pode trocar o comportamento sem editar ali. É a unidade de tudo que vem depois: se você não sabe colocar um seam, não sabe testar, não sabe fatiar, e não sabe delegar para um agente.

Tempo: ~15 min · Código: code/0001-seam/SeamDemo.java (roda com java SeamDemo.java) · Glossário: seam, adapter, interface

1 · A intuição

Pegue um suéter. Ele não foi cortado de um pano só — ele tem costuras: a manga encontra o corpo numa linha específica. Essa linha é uma decisão de quem fez a peça.

Agora suponha que você queira uma manga diferente. Existem dois caminhos:

Sem costura

Você pega a tesoura e corta o tecido. Funciona uma vez. Fica uma borda desfiada. Se você mudar de ideia, cortou de novo.

Na costura

Você descose, tira a manga, põe outra, costura de volta. O tecido do corpo nunca foi tocado. Você pode fazer isso quantas vezes quiser.

A costura é o lugar onde você troca uma parte sem cortar o resto. É exatamente isso que a palavra significa em código — e não é metáfora inventada por professor: é a palavra que Michael Feathers escolheu, e ele escolheu essa porque é essa a imagem.

Para uma criança de cinco anos

O abajur não está grudado na parede. Ele tem um plugue. Se você quiser um abajur diferente, você não quebra a parede — você desliga um e liga outro. A tomada é a costura.

2 · O mecanismo

A definição de Feathers, do próprio livro — é uma definição emoldurada, das poucas que ele destaca em caixa no texto:

Seam
A seam is a place where you can alter behavior in your program without editing in that place.

Michael C. Feathers, Working Effectively with Legacy Code, Cap. 4, p. 31 (caixa de definição; repetida na p. 36) verbatim, fonte primária

Leia devagar a parte que faz o trabalho: without editing in that place. Não é "sem editar". É sem editar ali. O comportamento muda; o arquivo onde o comportamento está escrito, não.

O repositório de skills carrega essa definição — e a atribui explicitamente:

Seam (Michael Feathers) — a place where you can alter behaviour without editing in that place; the location at which a module's interface lives. Where to put the seam is its own design decision, distinct from what goes behind it.

codebase-design/SKILL.md:22 verbatim

A segunda metade dessa frase é do próprio repositório, não de Feathers: onde colocar o seam é uma decisão de design separada de o que fica atrás dele. Muita discussão de arquitetura confunde as duas.

A mesma coisa, vista do outro lado

O repo define seam uma segunda vez, em outro skill — e é aí que a ideia fica poderosa:

A seam is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

tdd/SKILL.md:20 verbatim
A ideia central da lição

Essas duas definições não são dois conceitos que dividem um nome. São um conceito visto de dois lados.

O lugar onde você pode trocar comportamento é exatamente o lugar de onde você pode observar comportamento. Design e teste atravessam a mesma linha. É por isso que o repo diz: "The interface is the test surface. Callers and tests cross the same seam."

Consequência prática: quando um teste é difícil de escrever, isso quase nunca é um problema de teste. É o código dizendo que não tem seam ali.

3 · Em Java

A regra, no domínio bancário do curso: uma transferência acima de 10.000 é recusada durante a madrugada (22:00–06:00) e espera a manhã seguinte.

As duas versões abaixo têm a mesma regra, a mesma lógica de branch, o mesmo número de linhas. A única diferença é de onde vem a resposta para "que horas são".

NightGuardNoSeam.javasem seam
static final class NightGuardNoSeam {

    boolean allows(BigDecimal amount) {
        LocalTime now = LocalTime.now(ZONE);   // <-- hard-wired. No seam.
        return !(isNight(now) && amount.compareTo(LIMIT) > 0);
    }
}
NightGuard.javacom seam
static final class NightGuard {

    private final Clock clock;

    NightGuard(Clock clock) { this.clock = clock; }   // <-- o enabling point

    boolean allows(BigDecimal amount) {
        LocalTime now = LocalTime.now(clock);  // <-- observado através do seam
        return !(isNight(now) && amount.compareTo(LIMIT) > 0);
    }
}

O detalhe que a maioria passa batido

java.time.Clock existe no JDK para exatamente isso. Ele não é uma interface que alguém inventou para agradar testes — é a resposta oficial da plataforma ao problema de "o tempo é uma dependência escondida". Quando você injeta um Clock, você não está aplicando um truque de teste: está usando o seam que os projetistas da linguagem já colocaram lá.

Vale como princípio geral: prefira os seams que a plataforma já te deu antes de esculpir os seus.

4 · A regra que decide se um seam vale a pena

Seam não é de graça. Cada um é uma indireção a mais para quem lê o código. O repositório dá o critério em uma linha:

One adapter means a hypothetical seam. Two adapters means a real one. Don't introduce a seam unless something actually varies across it.

codebase-design/SKILL.md:65 verbatim

E o corolário, mais afiado ainda: "A single-adapter seam is just indirection." — DEEPENING.md:29

No nosso exemplo o seam é real, e é fácil auditar isso: Clock.systemDefaultZone() em produção, Clock.fixed(…) no teste. Dois. Se existisse só um, seria uma interface a mais para ler e nada a mais para ganhar.

Antes de continuar — responda de memória: por que "produção + teste" já conta como dois adapters?

Porque o teste é um caller de verdade, não um observador externo. Ele atravessa a mesma interface que o código de produção atravessa — é isso que "the interface is the test surface" quer dizer. O comportamento realmente varia através daquele seam: em produção o tempo anda, no teste ele fica parado. Variação real, dois adapters, seam justificado.

É por isso que "vou precisar disso um dia" não conta. Seam hipotético é indireção paga adiantado.

5 · A fonte primária

Michael C. Feathers, Working Effectively with Legacy Code — Prentice Hall PTR (Pearson), Upper Saddle River, NJ, 2005, xxi + 434 p. O livro onde o termo foi cunhado. O Seam Model é o Capítulo 4, "The Seam Model". capítulo localizado — ToC da editora

Nota de proveniência — vale ler, porque é a lição de evidência acontecendo. Este capítulo passou por três estados nesta mesma sessão: não confirmado (só notas de leitura de terceiros; o ToC da O'Reilly retorna 403) → capítulo localizado (ToC da editora) → texto conferido (o livro em mãos). Cada citação desta seção traz agora a página impressa. O ano também se moveu: circula muito como 2004; editora e catálogo dizem 2005.

Duas versões circulam — agora dá para arbitrar. Fowler renderiza "…without editing in that place"; outras fontes secundárias renderizam "A Seam is a place to alter program behavior, without changing the code." Confrontado com o livro: Fowler está exato, palavra por palavra. A outra é paráfrase de terceiro. Se você encontrar a segunda por aí, não cite como se fosse Feathers.

Feathers não escreveu sobre design bonito. Ele escreveu sobre código que já existe, não tem teste, e você precisa mudar sem quebrar. A definição de seam nasce dessa pressão — por isso ela é sobre onde você consegue entrar, e não sobre como deveria ter sido feito.

O que o repositório de skills não carregou de Feathers

O repo para na definição de seam. Feathers não para: ele pareia todo seam com um enabling point, e essa também é uma definição emoldurada:

Enabling Point
Every seam has an enabling point, a place where you can make the decision to use one behavior or another.

Feathers, Cap. 4, p. 36 verbatim, fonte primária

E a frase que explica por que o conceito precisa existir:

When you have a seam, you have a place where behavior can change. We can't really go to that place and change the code just to test it. The source code should be the same in both production and test.

Feathers, Cap. 4, p. 36 verbatim

O seam é a linha; o enabling point é a maçaneta. Um seam sem enabling point acessível é uma linha que você não consegue abrir.

O exemplo do próprio Feathers é o nosso exemplo — e ele diz a frase que faltava

Feathers monta exatamente o mesmo par que montamos na seção 3, em Java. Primeiro o caso sem seam, onde o objeto é criado dentro do método:

public Spreadsheet buildMartSheet() {
    Cell cell = new FormulaCell(this, "A1", "=A2+A3");
    cell.Recalculate();
}

Is the call to Recalculate an object seam? No. There is no enabling point. We can't change which Recalculate method is called because the choice depends on the class of the cell. The class of the cell is decided when the object is created, and we can't change it without modifying the method.

Feathers, Cap. 4, p. 41 verbatim

E então a versão que recebe a dependência em vez de criá-la:

public Spreadsheet buildMartSheet(Cell cell) {
    cell.Recalculate();
}

Is the call to cell.Recalculate in buildMartSheet a seam now? Yes. … Where is the enabling point? In this example, the enabling point is the argument list of buildMartSheet.

Feathers, Cap. 4, p. 42 verbatim

Compare com o nosso SeamDemo: NightGuardNoSeam constrói o tempo dentro do método — sem enabling point. NightGuard(Clock clock) recebe — e o enabling point é a lista de argumentos do construtor. Não é analogia nossa: é a estrutura que Feathers descreve, na letra dele.

Os três tipos de seam

Feathers deriva a taxonomia de um lugar não óbvio: "look at all of the steps involved in turning the text of a program into running code on a machine. Each identifiable step exposes different kinds of seams." Cada etapa do build vira uma oportunidade de troca.

TipoEtapa do buildOnde fica o enabling point
Preprocessing seamAntes do compilador (só C/C++)Um #define — no exemplo dele, TESTING
Link seamLigação dos objetos compilados"always outside the program text" — makefile, script de build, IDE
Object seamRuntime, via despacho dinâmicoLista de argumentos, construtor, ou onde o objeto é criado

E o veredito dele, que vale para Java:

It is important to choose the right type of seam when you want to get pieces of code under test. In general, object seams are the best choice in object-oriented languages. Preprocessing seams and link seams can be useful at times but they are not as explicit as object seams. In addition, tests that depend upon them can be hard to maintain.

Feathers, Cap. 4, p. 44 verbatim

Repare que link seam tem o enabling point fora do texto do programa — e Feathers avisa: "This makes the use of link seams somewhat hard to notice." É a mesma razão pela qual configuração escondida em script de build é difícil de auditar, com ou sem teste.

6 · O paralelo com agentes

Agora a parte que amarra o curso inteiro. A tese: as propriedades que tornam um código tratável para um mantenedor humano tornam ele tratável para um LLM — e seam é o primeiro caso.

Um seam é onde uma tarefa pode ser cortada

Quando você delega trabalho a um agente, a pergunta operacional é: qual é o menor pedaço de contexto que ele precisa para fazer isso certo? Essa pergunta é a mesma pergunta de seam, com outro nome. Um module com seam limpo pode ser entregue com um contrato pequeno. Um sem seam exige carregar os callers junto — e contexto carregado é contexto gasto.

O repositório transforma isso em regra explícita, e é a prática mais transferível do conjunto:

Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam.

tdd/SKILL.md:22 verbatim

Repare no que essa regra realmente faz: ela força a decisão de onde testar a acontecer enquanto o humano ainda está na conversa, e antes de qualquer código. Um agente deixado sozinho com "escreva testes" produz cobertura difusa em toda superfície que ele encontrar. Com os seams acordados antes, o esforço cai nos caminhos críticos.

Onde este paralelo é nosso, e onde não é

Verificado: a Anthropic afirma, verbatim, que "Similar to the functions of a well-designed codebase, tools should be self-contained, robust to error, and extremely clear with respect to their intended use", e nomeia como anti-pattern as ferramentas que "merely wrap existing software functionality".

Nosso analogia: o mapeamento seam/deep module ↔ design de ferramenta. Uma verificação de termos no texto completo de "Writing effective tools for agents" por deep, shallow, module, information hiding, Ousterhout, Parnas retornou nenhum presente.

E o contra-sinal, que não vamos esconder: a posição declarada da Anthropic é que ferramentas de agente exigem repensar a prática de API, não herdá-la — "instead of writing tools and MCP servers the way we'd write functions and APIs for other developers or systems, we need to design them for agents". A analogia é uma lente útil. Não é uma afirmação deles.

Este bloco é o padrão de honestidade do curso inteiro. Sempre que uma correlação entre arquitetura de software e arquitetura de agentes aparecer, ela vem rotulada: verificado, cunhagem ou nossa analogia. Uma tese boa não precisa de citação inflada.

7 · Retrieval

Não releia o que está acima. Responda de memória — errar aqui é o que faz a lição grudar.

Pergunta 1 de 3

O que faz de um lugar um seam?

Sem editar ali. Essa é a palavra que carrega a definição. O comportamento muda; o arquivo onde ele está escrito não é tocado. As outras três descrevem coisas boas — observabilidade, medição, isolamento — mas nenhuma delas é o que Feathers definiu.

Pergunta 2 de 3

Quando um seam é real, e não hipotético?

"One adapter means a hypothetical seam. Two adapters means a real one." Cuidado com a última opção: callers não são adapters. Mil callers atravessando a mesma implementação não fazem o seam real — o que faz é algo variar através dele. Produção + teste é o par mínimo honesto.

Pergunta 3 de 3

No SeamDemo, o que mudou entre as duas versões?

LocalTime.now(ZONE) virou LocalTime.now(clock). A regra é byte-por-byte a mesma: mesmo limite, mesma janela, mesma comparação. Zero linhas da regra mudaram — e a cobertura foi de 1 branch para 2. É esse o formato de todo par ruim/bom deste curso: uma coisa muda, e você vê o efeito dela isolado.

Recall livre — a mais difícil: explique por que "teste difícil de escrever" quase nunca é um problema de teste

Porque callers e testes atravessam o mesmo seam. Se o teste não consegue observar o comportamento, é porque não existe lugar de onde observar — e se não existe lugar de onde observar, também não existe lugar de onde trocar. A dificuldade do teste é o sintoma; a ausência de seam é a doença.

O repositório coloca isso como critério de forma: "If you want to test past the interface, the module is probably the wrong shape." Quando você se pega querendo alcançar o interior de um module para testar, a resposta não é um mock mais esperto — é que o seam está no lugar errado.
