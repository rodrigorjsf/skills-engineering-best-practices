1 · Vocabulário de deep modules

Dono: codebase-design. Este é o único lugar autoritativo destas palavras no repositório.

Module

anything with an interface and an implementation. Deliberately scale-agnostic: a function, class, package, or tier-spanning slice.

codebase-design/SKILL.md:14 verbatim

_Avoid_: unit, component, service — e também layer, wrapper quando você quer dizer module.

Por que importa: a escala é deliberadamente indefinida. Uma função é um module. Um pacote é um module. Uma fatia que atravessa camadas é um module. Isso é o que permite o mesmo vocabulário funcionar do método ao sistema.

Interface

everything a caller must know to use the module correctly: the type signature, but also invariants, ordering constraints, error modes, required configuration, and performance characteristics.

codebase-design/SKILL.md:16 verbatim

_Avoid_: API, signature — "too narrow — they refer only to the type-level surface".

Esta é a definição mais radical do glossário e a que mais muda comportamento. Se a ordem de chamada importa, isso é interface. Se falha com null, isso é interface. Se é O(n²), isso é interface. Nada disso aparece na assinatura Java.

Framing rejeitado: "Interface as the TypeScript interface keyword or a class's public methods: too narrow — interface here includes every fact a caller must know." — codebase-design/SKILL.md:108

Relação: "A Module has exactly one Interface." — :99

A genealogia — e o que nela não se sustenta

A definição de seis itens não está no Parnas. PDF conferido Ele escreve "Its interface or definition was chosen to reveal as little as possible about its inner workings" — interface como artefato autoral, o que você decide revelar. O repositório diz everything a caller must know, escrito ou não. São objetos diferentes, e o repo não cita Parnas aqui.

Mas a categoria mais surpreendente da lista está, e pela mão dele. Parnas critica o próprio circular shifter por revelar uma ordenação desnecessária: "By prescribing the order for the shifts we have given more information than necessary and so unnecessarily restricted the class of systems that we can build without changing the definitions." Ou seja, ele conta ordering constraint como informação entregue pela definição do módulo — exatamente a tese do repo, em 1971.

E o termo information hiding não é cunhado no paper famoso. Parnas escreve The second decomposition was made using "information hiding" [4] as a criteria — as aspas e a referência são dele. [4] é Parnas, "Information Distribution Aspects of Design Methodology", Technical Report, Carnegie-Mellon University, 1971. O critério é enunciado no paper de 1972; o termo vem de um relatório companheiro anterior, também dele.

Localizadores. Publicado: Communications of the ACM, Vol. 15, No. 12, dez. 1972, pp. 1053–1058. As citações acima foram lidas no relatório técnico da CMU de 1971 (PDF livre), pp. 17, 18 e 25 desse relatório — não diferenciado linha a linha contra a CACM. Ver lição 0003.

Implementation

what's inside a module, its body of code. Distinct from Adapter: a thing can be a small adapter with a large implementation (a Postgres repo) or a large adapter with a small implementation (an in-memory fake). Reach for "adapter" when the seam is the topic; "implementation" otherwise.

codebase-design/SKILL.md:18 verbatim

Seam Michael Feathers

a place where you can alter behaviour without editing in that place; the location at which a module's interface lives. Where to put the seam is its own design decision, distinct from what goes behind it.

codebase-design/SKILL.md:22 — atribuído a Michael Feathers no próprio repo verbatim

O repositório carrega uma segunda definição, do lado do teste:

A seam is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

tdd/SKILL.md:20 verbatim

_Avoid_: boundary — "overloaded with DDD's bounded context. Say seam or interface."

As duas definições são a mesma coisa vista de dois lados: onde você pode trocar comportamento (design) é exatamente onde você pode observar comportamento (teste). Ver lição 0001.

A definição original, da fonte primária

O repo cita Feathers quase palavra por palavra. A caixa de definição do livro diz:

A seam is a place where you can alter behavior in your program without editing in that place.

Feathers, Working Effectively with Legacy Code, Prentice Hall PTR, 2005, Cap. 4, p. 31 texto conferido

Enabling point ausente do repositório

Every seam has an enabling point, a place where you can make the decision to use one behavior or another.

Feathers, Cap. 4, p. 36 (caixa de definição) texto conferido

O repositório de skills não carrega este termo — ele para na definição de seam. Mas Feathers o trata como inseparável: todo seam tem um. A razão está na frase seguinte dele:

When you have a seam, you have a place where behavior can change. We can't really go to that place and change the code just to test it. The source code should be the same in both production and test.

Feathers, Cap. 4, p. 36 texto conferido

Mnemônico: o seam é a linha; o enabling point é a maçaneta. Um seam sem enabling point acessível é uma linha que você não consegue abrir. Ver lição 0001.

Internal seam · External seam

A deep module can have internal seams (private to its implementation, used by its own tests) as well as the external seam at its interface. Don't expose internal seams through the interface just because tests use them.

codebase-design/DEEPENING.md:30 verbatim

Adapter

a concrete thing that satisfies an interface at a seam. Describes role (what slot it fills), not substance (what's inside).

codebase-design/SKILL.md:24 verbatim

Port

Define a port (interface) at the seam. The deep module owns the logic; the transport is injected as an adapter. Tests use an in-memory adapter. Production uses an HTTP/gRPC/queue adapter.

codebase-design/DEEPENING.md:19 verbatim
A fonte do padrão — e o único ponto onde o repositório sai dele

Alistair Cockburn, The Hexagonal (Ports & Adapters) Architecture, HaT Technical Report 2005.02, 2005-09-04, v 0.9. página baixada e conferida Intent, verbatim: "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases."

O exemplo dele é literalmente o do repositório: "Additional adapters for the same port thus include an SQL adapter, a flat file adapter, and most importantly, an adapter to a 'mock' database, one that sits in memory and doesn't depend on the presence of the real database at all."

A divergência: a regra do Cockburn é "The asymmetry to exploit is not that between left and right sides of the application but between inside and outside of the application." Um port dele fica na fronteira da aplicação. O internal seam do repositório — dentro da implementação, usado só pelos testes do próprio module — não existe no modelo hexagonal. Não é contradição; é escala diferente. Ver lição 0004.

E o mito: "The hexagon is not a hexagon because the number six is important, but rather to allow the people doing the drawing to have room to insert ports and adapters as they need." Não são seis camadas nem seis portas — é espaço em branco no desenho.

Depth · Deep module · Shallow module

Depth — leverage at the interface: the amount of behaviour a caller (or test) can exercise per unit of interface they have to learn. A module is deep when a large amount of behaviour sits behind a small interface, shallow when the interface is nearly as complex as the implementation.

codebase-design/SKILL.md:20 verbatim

Princípio: "Depth is a property of the interface, not the implementation." — :62

Framing rejeitado — e a atribuição é que falha

"Depth as ratio of implementation-lines to interface-lines (Ousterhout): rewards padding the implementation. We use depth-as-leverage instead." — codebase-design/SKILL.md:107

O repositório rejeita a métrica de Ousterhout e ainda assim cita a tese dele com aprovação no README: "The best modules are deep. They allow a lot of functionality to be accessed through a simple interface." — README.md:166-168

Resolvido — e a atribuição é que não se sustenta. texto conferido O Capítulo 4 foi lido na íntegra na 1ª edição. A palavra ratio aparece zero vez nas 188 páginas; formula aparece uma vez, e é referência cruzada à fórmula de complexidade do §2.1. A Figura 4.1 é uma imagem raster cujos únicos rótulos são Interface (cost: less is better) e Functionality (benefit: more is better) — sem números, sem eixos, sem equação. O que o livro diz é: "Module depth is a way of thinking about cost versus benefit." — 1ª ed., §4.4, ebook p. 35

Ele ainda rejeita contagem de linhas explicitamente, duas vezes: "Sometimes an approach that requires more lines of code is actually simpler, because it reduces cognitive load." (§2.2, ebook p. 20) e "Methods containing hundreds of lines of code are fine if they have a simple signature and are easy to read. These methods are deep." (§9.8, ebook p. 80).

Então: o framing rejeitado é uma simplificação folclórica real, que circula e que de fato premia inchar a implementação — mas o parêntese "(Ousterhout)" não tem base textual, e depth-as-leverage não corrige Ousterhout: restata a razão que ele escreve nas próprias notas de aula, "maximize functionality/(interface complexity)", cujos dois termos não são contagens de linha. Ver lição 0002 e docs/research/05-ousterhout-depth.md.

Metadados do livro. John Ousterhout, A Philosophy of Software Design. 1ª ed., abril de 2018, Yaknyam Press, ISBN 978-1-7321022-0-0 — Cap. 4, "Modules Should Be Deep", confirmado no Sumário do próprio livro. texto conferido A 2ª ed. (julho de 2021, ISBN 978-1-7321022-2-4) existe e é a edição linkada pelo repositório, mas o número e o título do capítulo de depth nela seguem não confirmados — o extrato oficial do autor contém apenas os Caps. 6 e 21. Páginas nunca se transferem entre edições. O debate público Ousterhout × Robert C. Martin é real (set/2024–fev/2025), mas trata de tamanho de método.

Leverage

what callers get from depth: more capability per unit of interface they learn. One implementation pays back across N call sites and M tests.

codebase-design/SKILL.md:26 verbatim

Locality

what maintainers get from depth: change, bugs, knowledge, and verification concentrate in one place rather than spreading across callers. Fix once, fixed everywhere.

codebase-design/SKILL.md:28 verbatim

The deletion test

Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep.

codebase-design/SKILL.md:63 verbatim

Forma operacional, para varrer um codebase inteiro: "Apply the deletion test to anything you suspect is shallow: would deleting it concentrate complexity, or just move it? A 'yes, concentrates' is the signal you want." — improve-codebase-architecture/SKILL.md:35 Concentra ou espalha é a formulação mais precisa: um refactor pode reduzir linhas e ainda assim destruir locality.

Pass-through é termo do Ousterhout — e ele não manda apagar

O repositório usa a palavra sem defini-la. Ela é o título de uma seção com caixa de alerta: "Red Flag: Pass-Through Method. A pass-through method is one that does nothing except pass its arguments to another method, usually with the same API as the pass-through method." — A Philosophy of Software Design, 1ª ed. 2018, §7.1, ebook p. 57 texto conferido Não conseguimos mostrar um elo de citação entre os dois; o termo é dele, a atribuição no repositório não existe.

O porquê liga esta entrada a depth: "Pass-through methods make classes shallower: they increase the interface complexity of the class, which adds complexity, but they don't increase the total functionality of the system." — §7.1, ebook p. 58

E o desfecho não é "apagar". A legenda da Figura 7.1 dá três saídas: expor a classe de baixo diretamente aos callers (b), redistribuir a funcionalidade entre as duas (c), ou fundir as classes (d). E o limite: "Having methods with the same signature is not always bad… Pass-through methods are bad because they contribute no new functionality." — §7.2, ebook p. 58 Ver lição 0005.

Red before green

Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.

tdd/SKILL.md:34 verbatim

Pre-agreed seams

Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything — agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

tdd/SKILL.md:22 verbatim

Esta é a dobradiça entre design e processo, e a prática mais transferível para trabalho agêntico. Consumida por implement ("Use /tdd where possible, at pre-agreed seams" — implement/SKILL.md:9) e acordada em to-spec.

Vertical slice · Tracer bullet tracer bullet: glossado nos docs, nunca definido num SKILL.md · Horizontal slicing

Horizontal slicing — writing all tests first, then all implementation. Bulk tests verify imagined behavior: you test the shape of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in vertical slices instead — one test → one implementation → repeat, each test a tracer bullet that responds to what the last cycle taught you.

tdd/SKILL.md:30 verbatim

O contraste mais nítido está no doc publicado:

A horizontal slice ships one layer of the change — all the schema, or all the API — and nothing works until every layer lands. A vertical slice, the tracer bullet, ships one narrow path through every layer at once, so it can be demoed the moment it's done.

docs/engineering/to-tickets.md:40 verbatim

Implementation-coupled anti-pattern

mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.

tdd/SKILL.md:28 verbatim

Tautological anti-pattern

the assertion recomputes the expected value the way the code does (expect(add(a, b)).toBe(a + b), a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth — a known-good literal, a worked example, the spec.

tdd/SKILL.md:29 verbatim

Este é o anti-pattern com formato especificamente de LLM. Um agente que escreve o teste para um código que ele mesmo acabou de escrever recalcula o valor esperado do mesmo jeito. O teste passa por construção e nunca pode discordar do código.

O que é um bom teste

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification — "user can checkout with valid cart" tells you exactly what capability exists — and survives refactors because it doesn't care about internal structure.

4 · Vocabulário de agentes

Fontes primárias externas. Aqui a disciplina de evidência importa mais, porque há bastante folclore circulando.

Smart zone · Dumb zone cunhagem, autoria rastreada

Fonte primária: Matt Pocock, Dictionary of AI Coding, entrada Smart zone.md — github.com/mattpocock/dictionary-of-ai-coding, commit 251fec7.

Early in a session the agent is in a "smart zone" — sharp, focused, recall is good. As the session grows it drifts into a "dumb zone": sloppier, forgetful, more mistakes — and more faithfulness hallucinations. Same model, same harness — just more context. The felt effect of attention degradation. On frontier models, the dumb zone commonly begins around 125K-150K tokens — though this is debated. Clear or compact when the session bloats; don't push through.

Dictionary of AI Coding, dictionary/Smart zone.md verbatim

The zones don't track the context window limit. A session can be deep in the dumb zone with most of the window still free: the limit is where the harness refuses to continue, but quality falls off long before that. Plan around the smart zone, not the window.

mesma entrada verbatim
Três correções ao que circula online
  1. A cifra "~100K tokens / ~40% da janela" NÃO está na fonte de Pocock. unverified Ela aparece só em resumos de terceiros. A fonte escrita dele diz "around 125K-150K tokens — though this is debated" e afirma explicitamente que as zonas não acompanham uma porcentagem da janela.
  2. "Cunhado por Dex Horthy (HumanLayer)" é unverified. O documento primário da HumanLayer foi buscado e a expressão "dumb zone" não aparece nele. O que é dele é o número 40–60% de utilização e o conceito de intentional compaction.
  3. A cunhagem fica em aberto. A afirmação defensável: "'Dumb zone' é definido por Matt Pocock no Dictionary of AI Coding; quem usou a expressão primeiro é unverified."

Vizinhos verificáveis — use estes quando precisar de evidência, não de vocabulário: context rot (18 modelos medidos), lost in the middle (revisado por pares), RULER (comprimento efetivo ≪ anunciado).

Attention budget · Attention degradation cunhagem

Each token has a finite amount of influence to distribute across the rest of the context… The budget is per-token and doesn't grow when the context does, which is why long sessions dilute.

Pocock, Dictionary of AI Coding verbatim

An instruction that was the loudest thing at 10k tokens of context is background hum at 150k. This is the mechanism behind attention degradation: the model doesn't forget; the signal gets lost in the noise.

idem verbatim

Este é o modelo mental dele, não ciência de transformers estabelecida. A Anthropic usa "attention budget" independentemente, então é vocabulário compartilhado de praticantes — mas o trabalho mecanicístico citável é outro (§5 da pesquisa 03).

Harness vocabulário de fornecedor estabelecido

An agent harness (or scaffold) is the system that enables a model to act as an agent: it processes inputs, orchestrates tool calls, and returns results.

Anthropic Engineering, "Demystifying evals for AI agents", 9 jan 2026 verbatim

Everything around the model that turns it into an agent: tools, system prompt, context-window management, permissions, hooks. Claude.ai and Claude Code run on the same model but behave differently because their harnesses differ.

Pocock, Dictionary of AI Coding, Harness.md verbatim

E a consequência diagnóstica: "When behaviour differs between two products, or between yesterday and today, the model is often not the variable — the harness is."

Harness engineering cunhagem rastreada

Fonte primária: Mitchell Hashimoto, "My AI Adoption Journey", 5 fev 2026. Ele se identifica como quem cunhou:

I don't know if there is a broad industry-accepted term for this yet, but I've grown to calling this "harness engineering."

Hashimoto, 5 fev 2026 verbatim

A prática: sempre que o agente erra, faça uma correção permanente no ambiente dele — documentação melhor, uma ferramenta nova, um check — de modo que ele não possa cometer aquele erro de novo.

Relação com "test harness": nossa analogia. Nenhuma fonte primária afirma que o uso em IA é um empréstimo deliberado do termo de engenharia de software. O que é verificável é que os dois convergem estruturalmente: ambos são o andaime não-produto que torna um artefato inerte executável e observável.

Deep tools nossa analogia

Rotulado com precisão — a Anthropic não faz esta analogia

Uma verificação de termos no texto completo de "Writing effective tools for agents" por deep, shallow, module, information hiding, Ousterhout, Parnas: nenhum presente.

O que a Anthropic diz, verbatim: "More tools don't always lead to better outcomes. A common error we've observed is tools that merely wrap existing software functionality." E: "Similar to the functions of a well-designed codebase, tools should be self-contained, robust to error, and extremely clear with respect to their intended use."

E o contra-sinal, que não deve ser suprimido: "instead of writing tools and MCP servers the way we'd write functions and APIs for other developers or systems, we need to design them for agents" — a posição declarada da Anthropic é que ferramentas de agente exigem repensar a prática de API, não herdá-la.

A analogia deep module ↔ deep tool é nossa, é forte e defensável, mas o documento não pode dar a entender que a Anthropic a fez.

5 · Vocabulário de alinhamento humano × agente

Dono: grilling, grill-with-docs, wayfinder. Fonte primária adicional: o AI Coding Dictionary do autor.

Grilling cunhagem dele, com ancestral reconhecido

A technique for developing a design concept with an agent: the agent interviews the user Socratically, one decision at a time, proposing a recommended answer for each. Slows the rush to a finished plan — no handoff artifact is written until the concept stabilises.

aihero.dev/ai-coding-dictionary/grilling verbatim
Por que a técnica existe — a frase mais importante do glossário

The technique exists because agents fill gaps silently. Asked to write a spec from a two-line prompt, the agent doesn't stop at the decisions you haven't made — it picks defaults and writes them in. … Grilling inverts this — instead of guessing, the agent has to ask.

idem verbatim

Guarde "agents fill gaps silently". É o diagnóstico inteiro em três palavras. O problema não é o agente errar — é ele não sinalizar que decidiu. Toda decisão que você não tomou vira um default escrito com a mesma confiança das decisões que você tomou.

O ancestral, reconhecido por ele próprio:

Before AI came along, devs called this rubber ducking — talking through your idea until you figured out all the permutations.

"My 'Grill Me' Skill Went Viral", 23 mar 2026 verbatim

A diferença com o pato de borracha: o pato não pergunta de volta. Grilling é rubber ducking onde o pato tem opinião, faz a pergunta seguinte, e recomenda uma resposta a cada passo.

HITL · AFK a classificação é dele

Every ticket is either HITL — human in the loop, worked with a human who speaks for themselves — or AFK, driven by the agent alone. A HITL ticket only resolves through that live exchange; the agent never stands in for the human's side of it (a grilling agent that answers its own questions has broken this).

E o modo de falha do AFK, que vale decorar:

The characteristic failure is coming back to hours of finished, confident work built on a wrong call made in the first ten minutes. The work isn't sloppy — it's coherent, just coherent about the wrong thing.

aihero.dev/ai-coding-dictionary/afk verbatim

Este é o argumento econômico do grilling em uma frase. O custo de uma decisão errada não é o erro — é tudo que foi construído coerentemente em cima dele. Grilling é caro; descobrir na sexta-feira é mais caro.
