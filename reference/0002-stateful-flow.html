O fluxo com estado

Se eu estou aqui, o que já existe e o que eu produzo? Esta página responde a essa pergunta sem que você precise reabrir o repositório.

Repositório: github.com/mattpocock/skills · Snapshot fixado: 2ab9580 · Cada referência arquivo:linha é um link para o blob nesse commit — a linha é a evidência · Complemento de Referência 0001 — Glossário, que é vinculante para todo termo aqui

Como usar esta página

Duas coisas diferentes estão mapeadas aqui e não devem ser confundidas. O grafo mostra controle: quem chama quem, e por qual porta você entra. A matriz mostra estado: qual arquivo cada skill escreve e quais skills o leem. Uma skill pode aparecer no grafo sem escrever nada, e um artefato pode sobreviver a todas as sessões que o produziram.

1 · A cadeia canônica esconde o aninhamento

O repositório publica uma única string de cadeia, idêntica em seis páginas de docs:

grill-with-docs → to-spec → to-tickets → implement → code-review

docs/engineering/grill-with-docs.md:47 · to-spec.md:56 · to-tickets.md:53 · implement.md:36 · tdd.md:44 · code-review.md:44 verbatim

Essa string achata duas chamadas aninhadas. O roteador do próprio repositório é mais preciso:

Either way, /implement builds each issue by driving /tdd internally — one red-green slice at a time — then closes out by running /code-review, a two-axis review (Standards + Spec) of the diff, before committing.

ask-matt/SKILL.md:26 verbatim

A página de docs do tdd confirma pelo outro lado, com a frase mais econômica do corpus inteiro sobre o assunto: "so tdd is the engine inside that step rather than a step of its own" (docs/engineering/tdd.md:47).

Ou seja: tdd e code-review não são etapas da cadeia — são o motor dentro da etapa implement. A topologia real é um main flow, três on-ramps, um ciclo, uma camada de vocabulário por baixo e uma pré-condição executada uma vez. Os termos main flow e on-ramp são do próprio repositório: "A flow is a path through the skills. Most paths run along one main flow, and two on-ramps merge onto it." (ask-matt/SKILL.md:11).

Anomalia interna. O texto diz two on-ramps, mas a seção "On-ramps" lista três: triage, diagnosing-bugs e wayfinder (:38, :42, :44). Contamos três.

2 · O grafo, em duas vistas

Duas figuras, não uma: o main flow tem uma forma linear e as entradas têm forma de estrela, e sobrepor as duas produz um emaranhado ilegível. A primeira responde "o que acontece se eu seguir em frente"; a segunda, "por onde eu entro e por onde eu saio".

3 · Percurso, passo a passo

Passo 0 — a pré-condição

/setup-matt-pocock-skills roda uma vez por repo (ask-matt/SKILL.md:78). Ele escreve três arquivos sob docs/agents/ e um bloco ## Agent skills em CLAUDE.md ou AGENTS.md — nunca cria o segundo se o primeiro existe (setup/SKILL.md:80).

Tudo a jusante resolve o issue tracker por esse ponteiro, nunca por um caminho hardcoded. Essa indireção foi ela mesma a correção de um bug: o wayfinder fixava literalmente docs/agents/issue-tracker.md e "silently fell back to the local-markdown tracker — even one whose CLAUDE.md clearly declares GitHub issues" (CHANGELOG.md:63).

Passo 1 — grill

/grill-with-docs é uma skill de uma linha de corpo: "Run a /grilling session, using the /domain-modeling skill." (grill-with-docs/SKILL.md:7). O que a torna a cabeça do fluxo é o rastro de papel: ela é stateful — CONTEXT.md e ADRs. Sua irmã /grill-me é a mesma primitiva sem artefato nenhum: "Stateless: it saves nothing locally, builds no CONTEXT.md" (ask-matt/SKILL.md:70).

Passo 2 — o desvio do prototype

Se uma pergunta "needs a runnable answer (state, business logic, a UI you have to see)", o fluxo desvia por /prototype — com /handoff nas duas direções (ask-matt/SKILL.md:18-21). É o único lugar do corpus onde uma skill é usada explicitamente como ponte bidirecional.

Passo 3 — o ramo multi-sessão

Multi-sessão → /to-spec e depois /to-tickets; sessão única → /implement aqui mesmo (ask-matt/SKILL.md:22-24). Os tickets são tracer bullet vertical slices, cada um declarando suas blocking edges — os tickets que precisam terminar antes que ele possa começar (to-tickets/SKILL.md:38). Ver glossário — vertical slice.

Higiene de contexto — a regra que amarra os passos 1 a 3

"Keep steps 1–3 in one unbroken context window — don't compact or clear until after /to-tickets […] Each /implement then starts fresh, working from the ticket." (ask-matt/SKILL.md:30). O limite é a smart zone: "the window (~120k tokens on state-of-the-art models) within which the model still reasons sharply" (:32).

tensão de número Esse ~120k é o número que esta skill declara. O número que Pocock dá no Dictionary of AI Coding, registrado no glossário, é "around 125K-150K tokens — though this is debated". São dois números do mesmo autor em dois lugares. Não os fundimos nem tiramos média — cite a fonte junto com o número.

Passo 4 — implement

/implement tem nove linhas de corpo. Ele lê a spec ou os tickets (implement/SKILL.md:7), dirige /tdd em pre-agreed seams (:9), roda typecheck e arquivos de teste isolados continuamente e a suíte inteira uma vez ao final (:11), chama /code-review (:13) e commita (:15). Ver glossário — pre-agreed seams.

As três on-ramps

A — /triage. Move issues por uma máquina de estados de cinco state roles e produz agent-ready issues que /implement pega depois (ask-matt/SKILL.md:38). A exclusão é explícita e vale a pena decorar: "Triage is only for issues you didn't create […] Tickets that /to-tickets produced are already agent-ready, so don't triage them." (:40).

B — /diagnosing-bugs. Entrada autônoma para qualquer coisa quebrada. O post-mortem tem uma saída arquitetural: "If the answer involves architectural change (no good test seam, tangled callers, hidden coupling) hand off to the /improve-codebase-architecture skill" (diagnosing-bugs/SKILL.md:134). O gatilho é a ausência de seam correto: "If no correct seam exists, that itself is the finding." (:114).

C — /wayfinder. Para o esforço grande demais para uma sessão. O ponto de entrega é deliberadamente to-spec, não implement: "Looping the map straight into /implement skips that collapse and throws the linked detail away" (ask-matt/SKILL.md:46).

Vocabulário do wayfinder que o glossário ainda não carrega — definido aqui, sem link porque não há âncora. Destination: "what reaching the end of this map looks like" (wayfinder/SKILL.md:34). Frontier: "the open, unblocked, unclaimed children — the edge of the known" (:69). Fog of war: "the dim view of decisions and investigations you can tell are coming but can't yet pin down" (:84).

O ciclo

/improve-codebase-architecture é a única skill que realimenta a cabeça do fluxo: "It surfaces deepening opportunities; picking one generates an idea you can take into the main flow at /grill-with-docs. It's the survey that finds the candidates; /codebase-design (below) is the bench you design the chosen one on." (ask-matt/SKILL.md:52). Ver glossário — deepening opportunity.

A camada de vocabulário

Duas referências model-invoked rodam por baixo de todas as outras: "each the single source of truth for its vocabulary. Reach for them directly when the words, not the process, are the problem" (ask-matt/SKILL.md:56). São /domain-modeling (a linguagem do domínio) e /codebase-design (a linguagem da forma do módulo). Na prática o /grilling é a terceira: é a primitiva de entrevista, e é ela que grill-with-docs significa quando diz "run a grilling session".

A distinção que decide se você escreve ou só lê

Ler CONTEXT.md não é a skill domain-modeling. O repositório separa isso de forma explícita: "Merely reading CONTEXT.md for vocabulary is a one-line prose pointer, not the domain-modeling skill. Only the active build/sharpen discipline (challenge terms, edge-case scenarios, write ADRs, update CONTEXT.md inline) is domain-modeling." (.agents/invocation.md:20).

É por isso que a coluna "Escreve" da matriz abaixo tem domain-modeling sozinho em três linhas, enquanto a coluna "Lê" tem seis skills. Passivo é habito; ativo é skill.

5 · Durabilidade — o que sobrevive a quê

Ordenado por quanto tempo o artefato dura depois que a sessão que o criou morre.

  1. CONTEXT.md + docs/adr/ — permanentes, commitados, o substrato de vocabulário. Criados lazily: "Create files lazily — only when you have something to write." (domain-modeling/SKILL.md:40).
  2. docs/agents/*.md + o bloco ## Agent skills — configuração permanente, escrita uma vez, lida por tudo.
  3. O issue tracker (specs, tickets, agent briefs, mapas de wayfinder, labels) — o meio compartilhado entre múltiplos agentes e múltiplos humanos. É o único artefato que suporta concorrência: "expect other sessions to be editing the tracker concurrently" (wayfinder/SKILL.md:128).
  4. .out-of-scope/*.md — memória institucional de rejeições, com uma guarda explícita: nada de já-implementado entra ali, "recording it would poison the dedup checks with false rejections" (OUT-OF-SCOPE.md:88).
  5. Branches descartáveis (research/<name>, prototype) — evidência retida, fora da main, nunca mergeada.
  6. Handoff doc e relatório HTML — deliberadamente efêmeros, no temp do SO.
Duas skills escolhem o temp do SO de forma independente

handoff: "Save to the temporary directory of the user's OS - not the current workspace" (handoff/SKILL.md:8). improve-codebase-architecture: "Write a self-contained HTML file to the OS temp directory so nothing lands in the repo" (:39).

A regra que as duas expressam: um artefato transitório não vira estado do repositório. Se ele não é lido por outra skill, ele não pertence ao repo.

6 · Achados que só aparecem lendo o upstream

Uma referência morta. O explicador de issue tracker do setup ainda lista qa como consumidor do tracker — "Skills like to-tickets, triage, to-spec, and qa read from and write to it" (setup/SKILL.md:40) — mas qa vive em skills/deprecated/qa/. É uma inconsistência interna do upstream no snapshot 2ab9580, não um erro nosso.

Dependências são invocação em prosa, nunca link entre pastas. "Dependencies are expressed as /skill-style prose invocation ('Run the /grilling skill'), not deep ../other-skill/FILE.md cross-references." (.agents/invocation.md:16). É por isso que o grafo acima não pode ser derivado de imports — ele só existe em prosa, e é exatamente por isso que vale desenhá-lo.

O eixo de invocação é a única taxonomia. disable-model-invocation: true no frontmatter ⇒ user-invoked; ausente ⇒ model-invoked (.agents/invocation.md:5-6). Uma consequência dura: "A user-invoked skill may invoke model-invoked skills, but it can never reach another user-invoked skill." (:8). Isso explica a forma do desvio do passo 2: grill-with-docs e handoff são ambas user-invoked, então uma não pode chamar a outra — a ponte só existe porque o humano digita /handoff. prototype, model-invoked, é a única das três que uma skill consegue alcançar sozinha.

Confira você mesmo: prototype foi promovida a model-invoked — "Make the prototype skill model-invoked, so the agent can reach for it autonomously (and other skills can too)" (CHANGELOG.md:21). No snapshot atual ela não tem disable-model-invocation, mas handoff e grill-with-docs têm.

O frontier aparece duas vezes com sentidos vizinhos. Em to-tickets é "any ticket whose blockers are all done" (to-tickets:65). Em wayfinder ganha uma terceira condição — unclaimed — porque ali há concorrência real (wayfinder:69). Mesma palavra, um grau a mais de rigor onde vários agentes disputam.
