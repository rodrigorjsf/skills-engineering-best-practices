Padrões Java do curso

Os oito movimentos em Java que as lições 0001–0006 realmente ensinaram, reunidos num lugar só. Cada um traz o código, o número que a JVM mediu e a lição de origem. Nada aqui é novo: se um padrão não aparece numa lição e num programa que roda, ele não entra.

Domínio: Account · Transfer · Balance · Ledger · Java 25, modo single-file — cd code/000N-slug && java Arquivo.java, sem passo de compilação · Vocabulário vinculante: referência 0001 — glossário

Como ler este catálogo

Cada entrada tem sempre a mesma forma: o movimento em uma frase, o código antes e depois, o que foi medido — saída capturada do programa da lição, não texto escrito para parecer saída — e onde ler mais.

Todo bloco monoespaçado marcado como saída foi produzido rodando o programa nesta sessão. Onde uma linha foi omitida, é porque ela varia entre execuções, e isso está dito.

A tabela lista os padrões; esta lista carrega o que ela não carrega. Cada pergunta é de sim ou não, e um sim te entrega o padrão e encerra a triagem.

  1. A dependência nasce dentro do método? → 1
  2. Só o teste troca essa dependência? → 5
  3. O caller repete uma sequência em ordem fixa? → 2
  4. A ordem é obrigatória e invisível no tipo? → 3
  5. O teste precisa de outro backend inteiro? → 4
  6. Algum método público só repassa? → 6
  7. Alguma interface tem um implementador só? → 7
  8. Um tipo do fornecedor aparece na sua abstração? → 8

As duas primeiras decidem onde a dependência entra; a terceira e a quarta, quanto o caller carrega; as quatro últimas são auditoria de código que já existe. Nenhuma se responde olhando para a classe — todas se respondem olhando para quem a chama.

1 · Seam no parâmetro de construtor

O movimento. A dependência deixa de ser construída dentro do método e passa a ser recebida. O seam não é o Clock — é o lugar onde a interface Clock fica, e o enabling point é a lista de argumentos.

SeamDemo.javasem seam
static final class NightGuardNoSeam {

    boolean allows(BigDecimal amount) {
        LocalTime now = LocalTime.now(ZONE);   // <-- hard-wired. No seam.
        return !(isNight(now) && amount.compareTo(LIMIT) > 0);
    }
}
SeamDemo.javacom seam
static final class NightGuard {

    private final Clock clock;

    NightGuard(Clock clock) {
        this.clock = clock;
    }

    boolean allows(BigDecimal amount) {
        LocalTime now = LocalTime.now(clock);  // <-- observed through the seam.
        return !(isNight(now) && amount.compareTo(LIMIT) > 0);
    }
}

Os dois adapters que atravessam esse seam já vêm no JDK. O de teste é uma linha:

static Clock at(String isoLocalDateTime) {
    return Clock.fixed(
            Instant.parse(isoLocalDateTime),
            ZONE);
}

java.time.Clock foi acrescentado ao JDK exatamente para isto. Prefira sempre o seam que a plataforma já colocou lá antes de esculpir o seu — é evidência mais forte que uma interface inventada.

Medido. As três primeiras linhas da seção A variam com o relógio de parede e por isso foram omitidas; o contador de branches é literal e não varia:

A. NightGuardNoSeam — dependency created inside
   BRANCHES COVERED .............. 1 of 2
   the other branch is unreachable until the wall clock moves.

B. NightGuard — dependency accepted at a seam
   allows(25000) at 23:30 local .. false   (expected false)
   allows(25000) at 10:00 local .. true    (expected true)
   BRANCHES COVERED .............. 2 of 2

Rule verified end to end: YES
Rule source lines changed to get there: 0
What changed: where the dependency comes from, not what the rule says.

O que não mudou: a regra. Mesmo limite, mesma janela, mesma comparação — 0 linhas alteradas. A cobertura foi de um branch para dois. Lição 0001 →

2 · A sequência vai para dentro, e private é a alavanca

O movimento. As cinco instruções que o caller escrevia viram o corpo de post(Transfer), sem uma vírgula alterada, e os cinco métodos que elas chamavam ganham private. Depth é propriedade da interface, não da implementação: aqui a implementação é literalmente a mesma dos dois lados.

o caller do ShallowLedger6 métodos · 1 ordem · 1 invariante
ShallowLedger ledger = new ShallowLedger(clock);

ledger.open();
ledger.debit(t.from(), t.amount().add(t.fee()));
ledger.credit(t.to(), t.amount());
ledger.credit(FEES, t.fee());
if (!ledger.balanced()) throw new IllegalStateException("unbalanced");
ledger.commit();
o caller do DeepLedger1 método
DeepLedger ledger = new DeepLedger(clock);

ledger.post(t);

E o module, com o diff inteiro visível: cinco private, mais post.

    open();

    credit(t.to(), t.amount());
    credit(FEES, t.fee());

A armadilha que anda junto — inchar não aprofunda

O mesmo programa carrega um PaddedLedger: mesma interface pública, mesmo comportamento, corpo escrito da forma mais longa possível. A métrica folclórica linhas-de-implementação ÷ métodos-públicos o promove sem que nada tenha sido ganho.

C. What "impl-lines / interface-lines" would score

   PaddedLedger ........................ 32 impl / 2 public = 16.0

Repare na quarta linha: a métrica acerta o caso principal, e é por isso que ela circula. O defeito não é errar — é ser de graça.

3 · A ordem obrigatória vira um tipo

O movimento. Uma ordering constraint que vivia em prosa — chame reconcile() antes de total() — passa a ser expressa pelo tipo de retorno: total() não existe no tipo aberto, e o único produtor do tipo fechado é reconcile().

InterfaceDemo.javaa ordem mora em prosa
public interface Ledger {
    void post(Transfer t);
    void reconcile();
    BigDecimal total();
}
InterfaceDemo.javaa ordem mora no tipo
public static final class OpenBooks {

    public OpenBooks post(Transfer t) {
        ...
        return this;
    }

    public SettledBooks reconcile() {
        ...
        return new SettledBooks(List.copyOf(book));
    }
}

public static final class SettledBooks {
    private final List<Entry> book;
    SettledBooks(List<Entry> book) { this.book = book; }
    public BigDecimal total() { return sum(book); }
}

Medido, antes. Duas classes com assinaturas idênticas, um caller só, resultados diferentes — e nenhuma exceção:

   naive caller  post, post, total()
   against EagerLedger ...............      0.00   OK
   against StrictLedger ..............     -5.00   MONEY DESTROYED

Medido, depois. E o veredito não é afirmado: o programa chama o javac de verdade, em tempo de execução, contra um caller que pede total() cedo demais.

B. The one change — ordering moved into the type
   post, post, reconcile, total() ....      0.00   OK
   total() declared on OpenBooks ..... false
   post() declared on SettledBooks ... false
   only producer of SettledBooks ..... OpenBooks.reconcile()

C. Does the wrong order compile? Ask javac.
   caller asks total() too early ..... REJECTED

   WrongOrder.java:6: error: cannot find symbol
           return books.total();
                       ^
     symbol:   method total()
     location: variable books of type OpenBooks
   1 error

O placar honesto: mover a ordem para o tipo leva o compilador de 2 de 6 para 3 de 6 categorias de interface — score after section B ... 3 of 6. Modos de erro, invariantes e performance continuam em prosa. Uma lição que dissesse "seis" estaria vendendo o próprio truque melhor do que ele é.

4 · Um port, dois adapters — o real e o in-memory

O movimento. Um port de dois métodos, satisfeito por dois adapters que não têm nada em comum por dentro. O mesmo teste roda contra os dois sem uma linha de diferença. Adapter nomeia o papel, não a substância.

public interface AccountRepository {
    Optional<Balance> find(String account);
    void save(Balance balance);
}
FileAccountRepositorydisco
@Override public Optional<Balance> find(String account) {
    Path f = dir.resolve(account + ".txt");
    if (!Files.exists(f)) return Optional.empty();
    try {
        return Optional.of(new Balance(account,
                new BigDecimal(Files.readString(f).trim())));
    } catch (IOException e) {
        throw new UncheckedIOException(e);
    }
}
InMemoryAccountRepositorymapa
@Override public Optional<Balance> find(String account) {
    return Optional.ofNullable(store.get(account));
}

@Override public void save(Balance balance) {
    store.put(balance.account(), balance);
}

Medido. As contagens de linha saem do próprio arquivo-fonte, lido em runtime entre marcadores:

A. One port, two adapters, nothing alike inside
   methods on AccountRepository ...... 2
   FileAccountRepository lines ....... 17
   InMemoryAccountRepository lines ... 6
   substance behind the file one ..... java.nio, the disk
   substance behind the memory one ... a HashMap

   same test, file adapter ...........      0.00   balanced
   same test, memory adapter .........      0.00   balanced
   results identical ................. true
   test lines changed between them ... 0

   ACC-1 via a NEW file adapter ......    297.50
   ACC-1 via a NEW memory adapter ....      0.00
   where the substance actually is ... outside / inside

As três últimas linhas são a demonstração inteira. Um novo adapter de arquivo, criado do zero sobre o mesmo diretório, encontra R$ 297,50 esperando. Um novo adapter in-memory encontra zero: quando o objeto morreu, o dinheiro morreu junto.

O contra-dado — não meça "adapter pequeno" com régua

O glossário registra a distinção do repositório: small adapter with a large implementation (o repo Postgres) contra large adapter with a small implementation (o fake in-memory). As linhas medidas dizem o contrário — 17 contra 6. Não é contradição: "grande" e "pequeno" ali são proporções entre o shim e o que está atrás dele, não contagens. Aplicada com régua, a frase dá errado.

5 · Seam interno por fábrica não-pública

O movimento. A dependência é aceita — mas não pelo construtor público. Uma fábrica package-private dá ao teste o mesmo poder de substituição sem que nenhum caller precise aprender que a dependência existe. É a distinção internal seam × external seam escrita em modificadores de acesso.

O critério não é se algo varia — é quem varia. Clock tem um caller de produção que o escolhe: um job de replay. FeePolicy não tem nenhum. Os dois passam na regra dos dois adapters; só um pertence à porta da frente.

AdapterDemo.javaa porta pública e o seam interno
/** The public way in. Two things a caller must learn: repo, clock. */
public TransferService(AccountRepository repo, Clock clock) {
    this(repo, clock, STANDARD);
}

/** The internal seam. Not public — tests use it, callers can't see it. */
static TransferService withPolicy(AccountRepository repo,
                                    Clock clock,
                                    FeePolicy fees) {
    return new TransferService(repo, clock, fees);
}

private TransferService(AccountRepository repo, Clock clock, FeePolicy fees) {
    this.repo = repo; this.clock = clock; this.fees = fees;
}

Medido. Quem confirma que a interface pública não cresceu é a JVM, por reflexão sobre os construtores declarados:

B. Two dependencies. Only one belongs in the constructor.
   public constructors ............... 1
   things a caller must supply ....... 2  (repo, clock)
   FeePolicy in the public surface ... false
   withPolicy is public .............. false

   fee under the standard policy .....      2.50
   fee the test substituted ..........      0.00
   callers who had to learn it ....... 0

E o preço do desenho alternativo, com a FeePolicy içada para o construtor público, contado em vez de descrito:

D. The two designs, interfaces counted
   design A — caller must supply ..... 2
   design B — caller must supply ..... 3
   difference ........................ 1  (FeePolicy)
   same fee out of both designs ...... true
   verdict ........................... more interface, same behaviour

Parâmetro de construtor é interface — required configuration, a categoria 4 do padrão 3. Mais interface e mesmo comportamento é a definição de shallow, cobrada em parâmetro. Lição 0004 →

6 · Detecção de pass-through

O movimento. Um método pass-through é aquele cujo corpo não faz nada além de repassar para um método de mesmo nome. Em vez de julgar no olho, o programa lê o próprio arquivo-fonte, isola cada método público casando chaves, achata o corpo e testa a forma. O deletion test deixa de ser imaginado e passa a ser executado: dois conjuntos de callers reais, um com o module e outro sem.

TransferFacadetrês métodos, três repasses
public void post(Transfer t)  { ledger.post(t); }

public BigDecimal total()   { return ledger.total(); }

public Instant now()       { return ledger.now(); }
static final Pattern DECL =
        Pattern.compile("public\\s+[\\w.<>\\[\\]]+\\s+(\\w+)\\s*\\(");

// ...corpo achatado, chaves casadas, e então:
if (flat.matches("(return )?\\w+\\." + name + "\\([^)]*\\);")) forwarding++;

Medido. Três aplicações do mesmo teste, e a terceira é a que importa:

A. TransferFacade — delete it and see what comes back
   public methods ................... 3
   pure pass-throughs ............... 3 of 3
   caller lines with the module ..... 3
   caller lines without it .......... 2
   lines that reappeared ............ -1
   behaviour identical .............. true
   verdict .......................... delete it

B. Ledger.post — delete it and see what comes back
   call sites in this program ....... 3
   statements per call site ......... 5
   caller lines with the module ..... 4
   caller lines without it .......... 19
   lines that reappeared ............ +15
   behaviour identical .............. true
   verdict .......................... earning its keep

O −1 do caso A não é arredondamento: apagar a fachada saiu com lucro, porque a linha new TransferFacade(ledger) some junto. Já o +15 do caso B importa menos pelo número do que pelos três lugares em que essas linhas foram parar — locality destruída em tempo real.

O contra-dado — a técnica é binária e o defeito é proporcional 
C. AuditFacade — where the test answers badly
   public methods ................... 4
   pure pass-throughs ............... 3 of 4
   lines that reappeared ............ +3
   naive verdict .................... something reappeared: keep
   what actually reappeared ......... only receipt()
   share of interface that earned ... 1 of 4
   verdict .......................... neither keep nor delete

Ao pé da letra o teste aprova a AuditFacade — alguma complexidade reapareceu. E a resposta está errada: três dos quatro métodos não ganharam nada. Basta uma parte trabalhar para o teste devolver "keep". Aplique por método, não por classe, e quando a resposta sai misturada o movimento certo não é apagar nem manter: é redistribuir ou fundir.

7 · O detector de seam de um adapter só

O movimento. Sete linhas de reflexão que contam, para cada interface declarada, quantas classes a implementam. Um implementador é indireção; dois é um seam. É a regra de justificação transformada em contador que você pode apontar para um pacote Java de verdade.

static List<Class<?>> adaptersOf(Class<?> port) {
    return Arrays.stream(nested())
            .filter(port::isAssignableFrom)
            .filter(c -> !c.equals(port))
            .filter(c -> !c.isInterface())
            .collect(Collectors.toList());
}

Medido. O mesmo detector, nos dois programas em que ele aparece:

C. Adapters per port, counted from the class file
   AccountRepository adapters ........ 2
   NotificationPort adapters ......... 1
   NotificationPort methods .......... 1
   seam justified per SKILL.md:65 .... false
C. The single-adapter detector.
   FeeCalculator adapters ................ 1   just indirection
   LeakyPaymentPort adapters ............. 1   just indirection
   PaymentPort adapters .................. 2   real seam
O contra-dado — a contagem sozinha não é freio

A regra dos dois adapters traz o parêntese "(typically production + test)", que homologa um test double como o segundo adapter. Logo, qualquer dependência para a qual você aceite escrever um fake passa — que são quase todas. O que segura de verdade é a taxonomia de categorias de dependência, e os dois portões discordam:

D. Two gates. They do not agree.
   feeCalculator [in-process] ............ rule yes  gate no
   ledgerStore [local-substitutable] ..... rule yes  gate no
   notifier [remote-but-owned] ........... rule yes  gate yes
   paymentGateway [true-external] ........ rule yes  gate yes
   dependencies given .................... 4   given
   pass the two-adapter rule ............. 4   derived
   pass rule AND category gate ........... 2   derived
   ports the rule alone invents .......... 2   derived

Quatro passam na contagem, duas passam na taxonomia. As outras duas são o shadow codebase que Dan North descreve em option inversion. A categoria de cada dependência é given — classificação de projeto, não algo que a reflexão descubra; os vereditos e as somas são derivados.

8 · O port é declarado pela política

O movimento. A interface passa a morar ao lado de quem chama, com nome de quem chama, e o fornecedor a implementa. Aceitar a dependência é injeção; decidir que a abstração pertence à política é inversão. Os dois serviços abaixo aceitam; só um inverte.

InversionDemo.javainjeção sem inversão
public static final class NaiveTransferService {
    private final StripeGateway gateway;
    public NaiveTransferService(StripeGateway gateway) {
        this.gateway = gateway;
    }
    public Receipt transfer(Money amount) { return gateway.charge(amount); }
}
InversionDemo.javainjeção com inversão
public interface PaymentPort {          // declarado aqui, ao lado da política
    Receipt charge(Money amount);
}

public static final class TransferService {
    private final PaymentPort gateway;
    public TransferService(PaymentPort gateway) { this.gateway = gateway; }
    public Receipt transfer(Money amount) { return gateway.charge(amount); }
}

E a falha que "só use uma interface" não pega — a abstração que nomeia um detail do fornecedor na própria assinatura:

InversionDemo.javaa parte B falha
public interface LeakyPaymentPort {
    Stripe.Response charge(Money amount);
}

Medido. O teste da parte B é derivado, não afirmado: um detail é definido estruturalmente como um tipo cuja classe envolvente é o namespace do fornecedor, e a reflexão varre as assinaturas de cada port atrás deles.

A. Both accept the dependency. Only one inverts it.
   naive result .......................... 100.00
   inverted result ....................... 100.00
   same behaviour ........................ true

   NaiveTransferService takes ............ StripeGateway
     ...and that is an abstraction ....... false
   TransferService takes ................. PaymentPort
     ...and that is an abstraction ....... true
   swap the vendor without editing ....... TransferService

B. Part B: abstractions must not name details.
   PaymentPort leaks ..................... nothing
   LeakyPaymentPort leaks ................ Stripe.Response

Mesmo comportamento, mesmo resultado, mesma testabilidade — e um dos dois precisa ser editado quando a Stripe vira Adyen. O LeakyPaymentPort tem interface, tem injeção e tem um adapter, e ainda assim é inútil: qualquer segundo fornecedor teria que devolver um Stripe.Response. Lição 0006 →
